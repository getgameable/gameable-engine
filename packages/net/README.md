# gameable/net

## What

Multiplayer's engine side, with no Colyseus in it. The root entry is the wire protocol: the JSON text frames a client and the authority exchange, and the binary codecs for a player's input (client to server) and the transform rows of each send (server to client); it imports no DOM, no `ws` and no three, so the page and the server share it. The subpaths:

- `gameable/net/server`: our own `Room`, the `RoomGame` behind it, `createEngineRoomGame` (a guest as the authority on a headless engine), the `Replicator`, the inbound parser and budget, and the player store (`memoryStore`, `postgresStore`, `migrate`). `gameable/rooms/server` hosts the same `RoomGame` on Colyseus.
- `gameable/net/client`: the page side. `RoomConnection`, `createLoopbackConnection`, `multiplayer()` and its `net` service, `createClientLoop`, and the debug overlay's `net` lines.
- `gameable/net/solo`: Play Solo, the authority in the page.
- `gameable/net/page`: the boot logic multiplayer pages share: the `?room=` modes, solo or room server, the room badge, the catalog name.
- `gameable/net/testing`: loopback and latency transport pairs.

## When to use

You are writing a transport, a room, a replicator or a multiplayer page's boot. A game itself never imports this package: it uses `ctx.players` and `ctx.net` from `gameable`. `docs/concepts/multiplayer.md` has the model.

## Install

```sh
npm install --save-exact gameable
```

## Minimal example

```ts
import {
  decodeRows,
  encodeRows,
  RowFlag,
  rowsFrameBytes,
  type RowSink,
  type RowSource,
} from 'gameable/net';

// The lanes are read in place: hand back arrays you already own, never new ones per call.
const position = new Float32Array([1.5, 0, -2]);
const rotation = new Float32Array([0, 0, 0, 1]);
const scale = new Float32Array([-1, 1, 1]); // mirrored, and it arrives mirrored
const rows: RowSource = {
  count: 1,
  entity: () => 7,
  flags: () => RowFlag.POSITION | RowFlag.ROTATION | RowFlag.SCALE,
  position: () => position,
  rotation: () => rotation,
  scale: () => scale,
};
const out = new DataView(new ArrayBuffer(rowsFrameBytes(rows)));
const bytes = encodeRows(out, 600, 12, rows);

const sink: RowSink = {
  position: new Float32Array(3),
  rotation: new Float32Array(4),
  scale: new Float32Array(3),
  row: (entity, flags) => console.log(entity, flags, sink.position),
};
const header = decodeRows(new Uint8Array(out.buffer, 0, bytes), sink); // { frame: 600, ack: 12, count: 1 }
```

## API

`PROTOCOL_VERSION` (1) is what `hello` carries. `MAX_PAYLOAD_BYTES` (2,048) caps a `msg` payload by the UTF-8 length of its JSON; `MAX_CLIENT_TEXT_BYTES` caps a whole client text frame and is checked before `JSON.parse` runs, as is `MAX_JSON_DEPTH` (32), the deepest nesting of arrays and objects either side accepts.

Text frames are JSON discriminated by `t`: `ClientText` is `hello`, `msg` or `ping`; `ServerText` is `welcome`, `cmd`, `players`, `msg`, `pong` or `error`. `buildClientText` and `buildServerText` return the text or null (a payload over the cap, or a value JSON cannot carry); `parseClientText` and `parseServerText` return the checked frame or null. A parsed client frame is rebuilt from its checked fields, so nothing else it sent survives. `utf8ByteLength` counts bytes without encoding.

Binary frames start with a `FrameKind` byte and are little-endian. `encodeInput(out, seq, snapshot)` writes `INPUT_FRAME_BYTES` (111) bytes: kind 1, `seq` u32, the down, pressed and released key sets (`KEY_WORDS` u32 each), a mods byte, mouse `dx` and `dy` i16, wheel i8, the three button masks u8, focused u8. `decodeInput(bytes, into)` fills a caller-owned record and returns `{ seq }`.

`encodeRows(out, frame, ack, rows)` writes kind 2, `frame` u32, `ack` u32, `count` u16, then per row `entity` u32, `flags` u8 and only the lanes the flags name: position as three i32 millimetres (`RowFlag.POSITION`), rotation as one smallest-three u32 (`RowFlag.ROTATION`), scale as three f32, exact and signed (`RowFlag.SCALE`). `RowFlag.VISIBLE` (8: a hidden entity is now shown) and `RowFlag.TELEPORT` (16: snap, do not interpolate) carry no lanes and share their values with the engine's `TRANSFORM_FLAGS`. After the last row a frame may carry one 34-byte player trailer, written when `rows.player` is set: tag u8 (1), `entity` u32, `seq` u32 (the frame's `ack`), position as three exact f32, velocity as three f32, and a `PlayerRowFlag` byte (`GROUNDED` 1, `TELEPORT` 2: the authority teleported the body since this player's last rows). It is the receiving player's own body as the authority had it after the step that applied input `seq`, for client-side prediction; a spectator's frames have none, and a frame without it is the same bytes as before the trailer existed. `rowsFrameBytes(rows)` sizes the buffer. `decodeRows(bytes, sink)` writes each row's lanes into the sink's own arrays, then calls `sink.row(entity, flags)`, then `sink.player(row)` when the frame has a trailer and the sink asks for it; the returned header's `player` is the same `PlayerRow`, or null. A sink without `player` ignores the trailer, so a page that does not predict reads the frame as before. The room writes a trailer for every player whose entity has a moving body, read from the room's physics world at most once per step, and sends a rows frame that carries only the trailer when nothing else moved (a player held still is corrected too).

`packQuat` and `unpackQuat` are the rotation lane on its own: the largest component dropped and rebuilt, its index in 2 bits, the others 10-bit signed. Every function above is a thin call on one shared `InputCodec`, `RowsCodec`, `Quantizer` or `TextFrames`; `createInputCodec`, `createRowsCodec` and `createTextFrames` make one of your own.

The server entry, `gameable/net/server`, holds the rooms. `createRoom({ code, game, ports, maxPlayers?, sendHz })` seats players (ids 0 up, lowest free first: the first joiner is player 0, whose input is the guest's `ctx.input` and who gets the frame camera and HUD), coalesces each player's input frames between ticks (held keys latest, key and button edges OR-ed, mouse deltas summed), ticks itself at 60 Hz on `ports.setTimer`, and sends every connected player a `cmd` frame each tick, the authority's messages as `msg` frames from `AUTHORITY_SENDER` (not 0, which is a player) in the order the guest sent them, and a rows frame every `1000 / sendHz` ms when something moved. `room.handle(conn, frame)` and `room.disconnect(conn)` are its inputs; a disconnected seat is held for `leaveAfterMs` (10 minutes) and resumed by a `hello` carrying `seat: { id, secret }`. The game behind it is a `RoomGame`; `createEngineRoomGame({ definition | guest, manifest, readAsset?, physicsOptions?, maxPlayers?, seed, cullDistance?, prepareWorld? })` runs a real guest as the authority on a headless engine with Jolt, and its `Replicator` turns the world record into each player's commands and rows. The seats come from one place: the game's `features.multiplayer.maxPlayers` (sdk `roomSeats`). `createEngineRoomGame` reads it from the definition (the `maxPlayers` option is for a `guest`, which requires it because a wasm guest's seats cannot be read, or a game that declares no seats, default 8; one that disagrees with the declared seats throws), tells the guest `net.maxPlayers: seats - 1` (the highest id), and exposes it as `game.maxPlayers`; `createRoom` then needs no `maxPlayers` and throws on one that disagrees, so the room's door, the guest's slots and the game's declaration are the same number. The level is the manifest's: every entry whose `collider` is static (the default layer; a mesh with a `src`, a box or a sphere, at its `offset`) is a static Jolt body before the guest's `init`, read with `readAsset(url)` (default `fetch`; a Node host reads files). The guest's body ids are 1 to `physicsOptions.maxBodies` (default 4096); the level takes `maxBodies + 1` up, and the Jolt world is made for both, so the level costs the guest no id. `prepareWorld(world)` runs after the level, for what a manifest cannot declare. The run seed is one value: `seed` is both the game config's and the host's `seed()`, which `ctx.rng` follows. What the guest emits in `local-commands` never reaches a player, in the stream or in a welcome. The `welcome` and every `cmd` carry `entity`, the entity that player controls (the guest's `set-player-entity`: the SDK sends it for the join spawn and on `ctx.players.get(id).possess(e)`), or 0; with `cullDistance`, relevancy is measured from that entity's world position, and the entity and its parent chain are always relevant.

The player store is in the server entry too. A `PlayerStore` keeps one JSON document per player per game, plus one for the game itself (`loadGame`, `saveGame`). Each document has a `version`, which starts at 1 and goes up by one on every write, and a `savedAt` time from the store's clock. `save(game, player, data, expectedVersion)` writes only when the stored version is `expectedVersion` (0 for a player with no document yet). Otherwise it answers `{ ok: false, reason: 'stale' }` and writes nothing, so a room holding an old copy never overwrites a newer one. `exchange(game, a, b, apply, expected, note?)` changes two players' documents together or not at all. Both versions must match `expected`; `apply(docA, docB)` gets both current documents (`null` for none) and returns the two new ones, or `null` to say no. On success it returns both new versions. A document over `MAX_DOC_BYTES` (65,536 UTF-8 bytes) is refused as `size`, and text that is not JSON as `invalid`. `apply` returning `null` or throwing, or `a` equal to `b`, is `refused`. Every method resolves and none rejects: a store it cannot reach answers `unavailable`, and a load answers `null`.

`memoryStore()` keeps the documents in a `Map`, for Play Solo, tests, and a room server with no database. `postgresStore(url, { poolSize?, statementTimeoutMs?, connectTimeoutMs?, applicationName?, log? })` keeps them in Postgres. The defaults are 4 connections, a 5 s statement timeout and a 5 s connect timeout. Its tables are `player_data`, `game_data` and `exchanges` (a ledger with the exchange's `note`), created by the files in the package's `sql/` folder. `migrate(url, { dir? })` applies the files a database has not had yet, once each, in one transaction under an advisory lock, and records them in `schema_migrations`. A room server runs it once at start, before it opens the store; it is the one call here that rejects. A save is a compare-and-set on `version`. An exchange is one transaction that locks both rows with `select ... for update`, always in player-id order, so two opposite exchanges wait for each other instead of deadlocking. `pg` is imported on the store's first call, so the server entry still loads where `pg` cannot run.

Rooms use the store through `createEngineRoomGame({ ..., data: { store, game, log?, throttleMs? } })` (and `engineGame`, which passes it on). A join loads the player's document, keyed by `identity.id` (`seat-<id>` where the room resolves no identity, as in Play Solo), and hands it to the guest's `player-joined` as `{ doc, savedAt, now }` (`doc` and `savedAt` null for a player with no document; `now` is the server's clock, `PlayerHandle.joinedAt`, since the guest has none). The guest's `ctx.data.save` goes through `RoomData`: at most one write per player every `SAVE_THROTTLE_MS` (6 s), always flushed on leave and on dispose, in each player's order (a rejoin's load waits for the leave's write). `ctx.data.exchange` writes both players' pending saves, then calls `store.exchange` with `applyTransfer` (sdk) as `apply`; the `exchange-result` event reaches the guest on the next step after the store answers. The game's document arrives as a `game-data` event before the first step. A refusal (`stale`, `size`, `unavailable`) or a store that throws is logged and the room keeps running. Play Solo keeps one `MemoryStore` per `InPageAuthority`. `storeFromEnv(env)` is what `gameable serve` and the room server image start with: with `GAMEABLE_PG_URL` it runs `migrate` once and returns a Postgres store, and rejects (the server does not start) when it cannot; without it a `MemoryStore`, with one warning.

Identity is in the server entry too: `IdentityProvider` (`resolve({ token?, headers })` to a `PlayerIdentity` `{ id, name, kind: 'portal' | 'device' }` or null), `deviceIdentity(secret)` (signed `device.<random>.<hmac>` tokens, `mint()` and a constant-time verify), `portalIdentity({ authUrl, fetch })` (the auth service's `/auth/me`), `chain(providers)`, `createIdentities({ device, portal? })` (what a room asks at each join, minting a device token when the join has no valid one) and `identitiesFromEnv(env)` (`ROOMS_SECRET`, `GAMEABLE_AUTH_URL`, refusing a short secret in production). The room server is what asks them: see `gameable/rooms`'s README, "Identity". Our own `Room` (Play Solo) resolves no identity. It is all Web Crypto, so it runs in a page as well as on Node.

The client entry, `gameable/net/client`, is the page side. A `RoomConnection` is a link to one seat, whatever carries it: `join(request, events)` delivers the server's frames unchanged (`onText` with JSON text, `onRows` with a rows frame's bytes) and reports `onState` (`connecting`, `open` once the `welcome` arrived, `reconnecting` while a dropped link retries with the seat held, `closed` for good), and `sendInput`, `sendText` and `leave` go the other way. `createLoopbackConnection({ connect })` speaks our own frames to our own `Room` over a `Transport` (the room in the page, and tests): it sends the `hello`, keeps the seat the `welcome` names, and on a lost link opens a fresh transport and resumes it (backoff 400 ms x attempt, at most 4 s, 10 tries); a server `error` ends it. `multiplayer({ connection, name?, room?, maxPlayers? })` is the page's `multiplayer` feature over a given connection (it fails with "no room server connection" without one; `gameable/rooms/client`'s `multiplayer()` is the same loader with a `ColyseusConnection` to the room server as its default, and is what `clientFeatures` loads): its `net` module (order -90) is the `net` service, a `NetClient`, pings every 2 s of fixed steps, and does not join on init: the client loop's attach calls `net.start()`, so a page is seated only once its level, characters and sandbox have loaded. The `NetClient` has `state`, `localPlayer` (-1 before the welcome), `localEntity` (each frame's `entity`), `room` (the room code the welcome names: the one to show and share), `players`, `rtt`, `ack`, `stats` (`staleRows` and more), `send`, and the queues the client loop drains. `createClientLoop(engine, adapter, net, sandbox, options)` replaces the host loop on a multiplayer page: each fixed step it begins the step on the adapter, applies a new welcome's world (the old one despawned), the queued commands and the rows (each entity's last two rows, blended at a render frame one send interval behind the newest and written through the adapter's `setTransformFromHost`; a TELEPORT row snaps), sends one INPUT frame (never before the welcome; the sequence restarts at 1 after each welcome), and ticks the client-role guest, if any, with the authority's messages as `message` events from `AUTHORITY_SENDER`.

With `createClientLoop(..., { predict: true })` (the page reads `features.multiplayer.predict`) the page predicts its own character body; the page must register `physics()` with only the level's static colliders, or the loop throws at init. The movement runs in the client guest, not in the host: a game's movement is a system with `on: 'both'`, and on a client it walks `ctx.localPlayer` on a character body the client guest spawns for itself. That body is a local entity in the client's id range, so the client-role rules hold: no shared spawn, nothing replicated. The loop's `Predictor` takes the client guest's first `kind: 'character'` `add-body` as that body, applies its `move-character` and `remove-body`, and still drops every other physics command. The page's physics module steps the world. After each step the predictor keeps `{ seq, position }` and the move in a 64-step ring (`PredictRing`, one `Float64Array`) and writes the position onto `net.localEntity` (`setTransformFromHost` with `POSITION` only); that entity's rows then blend its rotation and scale only. At the start of each step the newest trailer is compared with the ring at its `seq`. More than 2 cm (`CORRECTION_METRES`) is a correction (`stats.corrections`): the body is set to the trailer's position and velocity, and every later step is replayed (its recorded move through the adapter's `moveCharacter`, then `world.step(1 / fixedHz)`). A trailer that says `TELEPORT`, names another entity, or is the first since the body appeared snaps the same way without counting. One for a `seq` the page has not sent since its last welcome (the old numbering, after a reconnect) is ignored, and a new welcome empties the ring. The predict path allocates nothing per step.

A page that stops stepping, or a link that stops delivering, is handled on the client. When the tab is hidden, the window blurs or the page hides, the `net` module sends one INPUT frame at once, outside any fixed step, with nothing held and `focused: false` (`releaseInput()`; the keys held in the last frame come up as `released` edges), so the room does not keep applying the last keys it heard while no steps run. The inbound queues are bounded at about 3 s of frames: 60 rows frames at the default `sendHz` 20, 180 `cmd` frames (the room's 60 Hz tick) and 256 messages. Rows are deltas, so an old frame cannot simply be dropped: past a cap all three queues are dropped, nothing more is queued, and at the next fixed step the client asks its connection for a fresh welcome (`RoomConnection.reconnect('resync')`, counted in `stats.resyncs`), so a tab left in the background holds kilobytes, not megabytes, and reconnects once, when it comes back. While joined, 2 s of fixed steps with no server frame (`silenceMs`; the room sends a `cmd` every tick) means a dead link the browser has not noticed, such as a Wi-Fi change that leaves the socket `OPEN`: the client calls `reconnect('silent')` (`stats.silences`) and shows `reconnecting` until the resume's welcome. Both count steps, not wall-clock time, so a tab coming back after minutes is not taken for a dead link. `reconnect(reason)` is part of every `RoomConnection`: the loopback one reopens its transport and resumes the seat with its secret; the Colyseus one closes the socket with `MAY_TRY_RECONNECT` (4010), which runs the SDK's own resume on the token. `net.onChange(listener)` hears `state`, `room`, `closeReason` and `lastWarning` changes as the frame that changed them arrives, so a page that draws no frames still hears them. An `error` frame that does not end the session (`isWarningError`; today only `budget`, the room dropping text frames over budget while the page keeps its seat) sets `lastWarning` and `stats.warnings`, never `closeReason`, and the loopback connection does not take it as a refusal: a later drop still reconnects. A drop whose close reason is `budget` (the room freed the seat for abuse) ends it.

The debug overlay's `net` lines: `multiplayer()`'s `bind(engine)` calls `showNetOnOverlay(engine, net)`, which, when the engine has an overlay (`createEngine({ debug: true })`), hands it `createNetOverlayLine(net).text` through `overlay.setExtra`. On F3 it reads `net    joined KQTX  players 2/6  rtt 34 ms` and `rows 20/s  stale 0  corrections 0  you entity 12, seat 0`: the state, the room code (`----` before the welcome), connected players over seats, the round trip, rows frames per second since the last redraw, `stats.staleRows`, `stats.corrections` (how often a predicting page's own body was put back where the authority had it; always 0 without `predict`), and `localEntity` and `localPlayer`. The overlay calls it only when it redraws (every 250 ms), never per frame. A headless engine, or a page without `debug`, gets nothing.

The solo entry, `gameable/net/solo`, is Play Solo: the authority in the page. `createInPageAuthority({ guest, definition, manifest?, physicsOptions?, prepareWorld?, seed? })` returns an `InPageAuthority`. `start()` boots the wasm `guest` through `createEngineRoomGame` on a headless engine with its own Jolt world (Jolt's module is the page's, through `loadJolt`'s singleton), builds the manifest's static colliders and runs `prepareWorld` before the guest's `init`, and opens our own `Room` (code `SOLO`, seats and `sendHz` from `definition`) on `SoloPorts`: a `PageClock` (simulated time that moves only when stepped) and one loopback pair per connection. `connection` is that run's `LoopbackConnection`, for the page's `multiplayer` feature; `drive(engine)` runs one room tick per fixed step of the page engine (each `engine:frame`'s `substeps`, so the page's `maxSubsteps` caps the authority too and a hidden tab pauses it; `step(n)` does it by hand); `stop()` closes the room (`error: ended`) and disposes the authority's engine, guest and Jolt world. A page starts it with `startPlaySolo({ ...the same options, dev: import.meta.env.DEV, warn })`, which, under `npm run dev`, first asks the dev server (`gameable/vite` answers at `GUEST_STATUS_PATH`) whether `build/guest/` is older than the game's sources and warns if so (`checkGuestStatus`, `staleGuestWarning`): the authority runs the built guest in every mode while the page's client guest runs the sources as they are, so a stale build means two sets of rules. When the authority cannot start, its error names `npm run build:guest`. A page that joins a remote room never loads this entry.

The page entry, `gameable/net/page`, is the boot both multiplayer pages share (the third-person template's and the mystery example's). `roomMode(location.search)` reads `?room=`: none or empty is `solo`, `new` and `quick` (any case) are those, and anything else is `join` with the code trimmed and upper-cased. `chooseRoom(mode, { game, name, startSolo })` starts the in-page authority only for `solo` and returns `multiplayer`, the overrides for `clientFeatures({ multiplayer })`: the solo run's connection, or the room server's `game`, `room` and `newRoom`. `createPageRoom({ net, mode })` puts the room badge in the corner (the code and a copy-link button in a room, a "Play with friends" button, to `?room=new`, when solo; with `browse: { game, list }`, a "Browse rooms" button, shown when solo only once `/health` answers, that opens `RoomBrowser`: the game's public rooms, each row's code, players/max and phase as text, a Join to `?room=CODE` (off for a full room), New room and Quick join; `list` is `gameable/host/features`' `listPublicRooms`, called only when the panel opens, and closing the panel closes the list) and, once joined after `new` or `quick`, rewrites the address to `?room=CODE` with `history.replaceState` (`rememberRoom`), so a reload resumes the seat. It follows `net.onChange`, so both happen in a tab that draws no frames; `frame()` does the same check by hand. `gameable/net/client`'s `attachRoomClient({ engine, net, adapter, sandbox, slot, room, loop?, onDead })` is the end of a page's boot, the same for every page: the client loop into the slot (which starts the join), Play Solo's `drive`, and the badge (it lives in the client entry so this one stays free of the client loop: the CLI reads `catalogName` here). `leaveRoom(engine)` gives up the seat at once when a boot fails or the client loop dies, so the others do not see a statue in it. `closeReasonText` and `netStatusText` are the badge's words. `catalogName(packageName)` is the game's room server name: the `package.json` name without its npm scope, the one rule the page, `gameable serve` and `game.json` share.

## Gotchas

The encoders and decoders allocate nothing, which means the header objects `decodeInput` and `decodeRows` return are reused by the next call: copy the fields you keep. An encoder returns 0 and writes nothing when the `DataView` is too small, or `encodeRows` when `count` is not an integer from 0 to 65,535. A decoder returns null, and never throws or reads past the end, for a frame that is short, long, of another kind, has an unknown row flag bit, a NaN or infinite scale, or whose `count` claims more rows than it holds; the rows sink is not called at all for such a frame. Pass the exact message bytes, not a larger reused buffer: trailing bytes are a malformed frame.

Quantisation: positions round to the nearest millimetre and clamp at ±2,147 km; scale is not quantised, so a mirrored -1 or a sky dome's 100 arrives as sent (a non-finite scale is sent as 1, and one past the f32 range as its limit); rotations come back within 1e-3 per component and with the sign canonicalised (the largest component positive), so compare against `q` or `-q`. Mouse deltas round to whole pixels and clamp to i16, the wheel to i8. A zero or non-finite quaternion encodes the identity. Server text frames are not size-capped, because `welcome` carries the world; `cmd` commands and the `welcome` snapshot are passed through unchecked.

A room hands `ports.send` its rows frames as borrowed bytes over one reused buffer: a port that keeps them past the call must copy them. The package opens no sockets: the room server (`gameable/rooms`, on Colyseus) carries production frames, and the transports here are the in-memory `loopbackPair` and `latencyPair`. The seat-secret resume (`hello` with `seat`) is Play Solo's, over that loopback. The authority's single `set-listener` goes to every player as it is: a room has no per-player listener. A shared entity whose parent is a local-only (`local-commands`) entity arrives as a root, at its local offset from the world origin: its parent is never named to a player.

On the client, a client-role guest makes no shared entity: the SDK runs no level `spawns` on a client, so its world is the authority's, replicated. Everything a client guest emits is applied on its own page and sent nowhere, except `send`, which goes up to the authority: its commands and local commands (sounds, HUD, local spawns, particles), its transforms, its camera and HUD unless the authority has set this player's own (the room sends those only when they change; the loop keeps showing the last one). Physics commands are dropped (on a predicting page, all but its own character body's). Its entity and sound ids live in a range the authority's never reach: entity `e` is drawn as `entityBase + e` (pass the game's `world.maxEntities` as the loop's `entityBase`; an authority entity id is a component-array index, always below it) and sound `s` as `0x40000000 + s`; the page's events about them are shifted back, and events about the authority's entities and sounds never reach the client guest. The client guest's own ECS holds only its local entities, so a client system that reads `Transform` does not see the replicated world (feeding it in is phase 6). A welcome replaces the queued commands and the queued authority messages: a message from before a reconnect's welcome is lost. The client loop never reads physics, even when a physics module is registered, unless `predict` is on. Then it steps the page's world and replays steps in it, which is why that world must hold nothing but the level and the one body. Prediction covers the body's position: its facing and animation still come from the authority's rows. The room coalesces input per room tick, so a link that delivers two INPUT frames in one tick has two client steps answered by one server step; that shows as a correction, which is what corrections are for. The ack can go backwards after a reconnect: treat it as information, never as an error. Two direct-mode guests in one realm share the SDK's component arrays, so once a second one starts, the first throws ("two direct guests in one realm") on its next tick: production rooms and Play Solo's authority run the wasm guest.

Player store: a store may reformat the JSON you saved (Postgres `jsonb` reorders keys and adds spaces), so parse `data`, never compare its text. `unavailable` means the write may or may not have happened. Load again before retrying, because the version you hold may now be stale. `apply` must be synchronous and pure: Postgres calls it while it holds both players' rows locked. JSON that Postgres cannot store, such as `�` inside a string, is `invalid` in both stores, so the memory store refuses what Postgres would. The store's log lines never carry the URL's password. A bundled room server must ship `packages/net/sql` as a `sql/` folder beside its bundle, or pass `migrate(url, { dir })`. Postgres refuses to run as root, so the store's database tests skip under root with one log line. They run against `embedded-postgres`, or against `GAMEABLE_PG_TEST_URL` when that is set (never `GAMEABLE_PG_URL`, which is a live server's database).

To test an authority without a room, `gameable/test` has the room's side of `frame-input`: `createPlayersInput(count)` is a tape of seats 0 up, each with its own input (`input(seat)`), where `join`, `leave` and `message` queue the events a room would and `frame()` returns that step's `players` (joined seats ascending, a leaver already out) and `events`; `observe(commands)` follows `set-player-entity` (`entityOf(seat)`). `simulatePlayers(guest, { frames, players?, script })` runs it like `simulate`, the script getting `(frame, tape)` (as in a room, `frame-input.input` is seat 0's input while seat 0 is joined, and neutral otherwise), and adds `views[frame]`: each joined player's entity, own HUD and camera, and the sends they received. Direct and wasm runs of one script must agree on `hashes` and `views`; run them in turn, never interleaved, because of the shared arrays above.
